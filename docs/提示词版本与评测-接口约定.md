## 一、要解决的问题

提示词目前是「改完直接生效」：谁改的、改了什么、有没有变差，全靠人盯。上线后一旦答歪，只能手改回去，
且改不回原样。本节这两块补的就是这个缺口：

| 能力 | 解决的问题 |
| --- | --- |
| **版本与发布** | 改动先落草稿 → 评测通过 → 按比例灰度 → 全量。出问题一键回滚到任意历史版本 |
| **效果评测** | 把「标准问法 + 标准答案」固化成用例，改完先跑分，通过率掉下来就拦住不发布 |

两者的关系：**评测是发布的前置关卡**，版本是评测的比较对象。

## 二、数据表设计

沿用项目现有规范：`cs_` 前缀、下划线命名、`BIGINT` 主键、`tenant_code` 多租户、`create_time` / `update_time` / `deleted`。
DDL 建议直接追加到 `docs/database/init.sql`（不要对生产重复执行 `DROP TABLE`）。

### 2.1 `cs_prompt_version` —— 提示词版本快照

```sql
CREATE TABLE `cs_prompt_version` (
    `id`             BIGINT       NOT NULL AUTO_INCREMENT COMMENT '版本ID',
    `tenant_code`    VARCHAR(64)  NOT NULL DEFAULT 'default' COMMENT '租户编码',
    `version`        VARCHAR(20)  NOT NULL COMMENT '版本号，如 v1.4.0',
    `target`         VARCHAR(64)  NOT NULL DEFAULT '平台默认' COMMENT '适用对象：模板名或"平台默认"',
    `status`         VARCHAR(16)  NOT NULL DEFAULT 'draft' COMMENT 'draft/gray/published/rolled_back',
    `gray_scale`     INT          NOT NULL DEFAULT 0 COMMENT '生效流量百分比，100=全量',
    `change_note`    VARCHAR(500) NOT NULL COMMENT '变更说明，必填，用于回溯',
    `config_json`    JSON         NOT NULL COMMENT '配置快照，结构同 GET /api/prompt/config 的响应',
    `creator`        VARCHAR(50)  DEFAULT NULL COMMENT '创建人姓名',
    `creator_id`     BIGINT       DEFAULT NULL COMMENT '创建人ID',
    `publish_time`   DATETIME     DEFAULT NULL COMMENT '最近发布时间',
    `rollback_time`  DATETIME     DEFAULT NULL COMMENT '最近回滚时间',
    `create_time`    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    `update_time`    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    `deleted`        TINYINT      NOT NULL DEFAULT 0,
    PRIMARY KEY (`id`),
    KEY `idx_tenant_target` (`tenant_code`, `target`, `status`),
    KEY `idx_create_time` (`create_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='提示词版本快照';
```

**关键约束（后端必须校验）**

1. **同一 `target` 下最多一个 `published`**。全量发布新版本时，同 target 的旧 `published` 需自动降级为 `draft`。
2. **`published` / `gray` 状态的版本不允许删除**，否则线上无处可回退。前端已做禁用，后端仍需兜底校验。
3. `config_json` 用 JSON 列而非拆字段：配置项会随产品迭代增加（本次就加了 `variablesConfig`），
   拆字段每加一项都要改表。

```sql
CREATE TABLE `cs_prompt_eval_run_detail` (
```

> 用例与期望答案在报告里存**快照**，不随时间变化：事后改了用例，历史报告仍要能复现当时的结论。

## 三、接口清单

统一响应体沿用项目现有约定：`{ code, msg, data }`，`code=200` 为成功。

### 3.1 版本与发布

#### ① `GET /api/prompt/version/list`

版本列表，按创建时间倒序。

**请求**：无参数（可选 `target` 过滤）

**响应**：
```json
{
  "code": 200,
  "data": [
    {
      "id": 7101,
      "version": "v1.4.0",
      "target": "电商售后专用",
      "status": "draft",
      "grayScale": 0,
      "changeNote": "新增「违规问题拒答话术」，开启提示词注入防护",
      "creator": "超级管理员",
      "createTime": "2026-09-15 10:20:00",
      "config": { }
    }
  ]
}
```

> 列表**必须带 `config`**：前端「版本对比」直接在这份数据上做字段 diff，不再单独拉详情。

#### ② `GET /api/prompt/version/{id}`

单个版本详情，响应 `data` 为上面数组里的单个对象。

#### ③ `POST /api/prompt/version/save`

保存为新版本（草稿）。

**请求体**：
```json
{
  "version": "v1.5.0",
  "target": "电商售后专用",
  "changeNote": "上下文条数 3→5",
  "status": "draft",
  "grayScale": 0,
  "config": { }
}
```

**后端要点**
- `changeNote` 为空要拒绝，返回 `msg: "请填写变更说明，方便日后回溯"`（前端已提示，后端需兜底）
- 有 `id` 则更新，无 `id` 则新增，`creator` 从登录态取，**不信任前端传值**
- 新版本一律存为 `draft`，即使是修改已有草稿

#### ④ `PUT /api/prompt/version/{id}/publish?grayScale=20`

发布或调整放量。`grayScale`：`100` = 全量发布，`0~99` = 灰度。

**后端要点（重要）**
- `grayScale >= 100` 时：同 `target` 下旧的 `published` 版本自动降级为 `draft`，`status` 置为 `published`
- `grayScale < 100` 时：`status` 置为 `gray`，**不动**现有全量版本（灰度版与全量版并存）
- 灰度分流按 `tenantCode + sessionId` 做一致性哈希，保证同一会话稳定命中同一版本，否则用户会看到回答忽好忽坏
- 返回 `msg` 直接展示给用户，如 `"已发布，20% 流量先跑"`

#### ⑤ `PUT /api/prompt/version/{id}/rollback`

回滚到指定版本。

**后端要点**
- 把该版本的 `config_json` 写回当前生效配置（`/api/prompt/config`）
- 同 `target` 下其它 `published` / `gray` 版本降级为 `draft`
- 该版本置为 `published` + `grayScale=100`，记录 `rollback_time`
- **回滚本身也要写操作审计**，这是最需要留痕的操作

#### ⑥ `DELETE /api/prompt/version/delete/{id}`

删除非生效版本。`published` / `gray` 状态返回失败：`msg: "正在生效的版本不能删除，先切到别的版本再删"`。

### 3.2 效果评测

#### ⑦ `GET /api/prompt/eval/set/list`

```json
{
  "code": 200,
  "data": [
    {
      "id": 8001,
      "name": "售后高频问题",
      "description": "退款、物流、改地址等最高频问法，决定大部分体感",
      "target": "电商售后专用",
      "caseCount": 5,
      "status": 1,
      "updater": "超级管理员",
      "updateTime": "2026-09-14 11:00:00"
    }
  ]
}
```
`caseCount` 由后端 `COUNT` 计算，前端直接展示。

#### ⑧ `POST /api/prompt/eval/set/save` · ⑨ `PUT /api/prompt/eval/set/update`

请求体为 `{ id?, name, description, target, status }`。`name` 必填且同租户内唯一。

#### ⑩ `DELETE /api/prompt/eval/set/delete/{id}`

**级联删除**该评测集下的用例与历史报告（含 `run_detail`）。前端文案已说明会一起删除。

#### ⑪ `GET /api/prompt/eval/case/list?setId=8001`

```json
{
  "code": 200,
  "data": [
    {
      "id": 8101,
      "setId": 8001,
      "question": "怎么退款？",
      "expected": "提交售后申请后 1-3 个工作日到账",
      "expectHit": "如何退款？",
      "mustRefuse": 0
    }
  ]
}
```

#### ⑫ `POST /api/prompt/eval/case/save` · ⑬ `DELETE /api/prompt/eval/case/delete/{id}`

常规增删，`question` 必填。

#### ⑭ `POST /api/prompt/eval/run`

跑一次评测，**同步返回报告**（前端用 `loading` 等待）。

**请求体**：
```json
{
  "setId": 8001,
  "target": "电商售后专用",
  "version": "v1.3.0"
}
```
`version` 为 `"当前配置"` 时，评测当前生效配置。

**响应**：完整报告对象（同 ⑯）。

**后端实现建议**
- 逐条调用现有问答链路（`/api/ai/chat` 或内部 Service），拿真实回答
- **判定规则**（三条，按优先级）：
  1. `mustRefuse=1`：回答属于「拒答话术」→ 通过；给了具体操作方案 → 不通过，`reason` 写
     `"应拒答却给出了具体方案，未走「违规问题拒答话术」"`
  2. `expectHit` 非空且不等于 `"—"`：召回复数里包含该知识 → 通过；未命中 → 不通过，
     `reason` 写 `"召回复数未命中「xxx」，落到兜底"`
  3. 其它：与 `expected` 做语义相似度比对，低于阈值判不通过，`reason` 写 `"兜底话术与期望口径不一致"`
- `score` 存相似度原始分，供人工复核阈值是否合理
- 用例量建议上限（如 200 条）并在超限时返回明确 `msg`，避免同步接口超时；**如果单次跑批可能超过 30 秒，
  建议改成异步任务 + 轮询，届时前端需相应调整**

#### ⑮ `GET /api/prompt/eval/run/list`

历史报告列表，**不返回 `details`**（避免列表接口随报告增多变重）。

#### ⑯ `GET /api/prompt/eval/run/{id}`

单份报告，含逐条 `details`：
```json
{
  "code": 200,
  "data": {
    "id": 8201,
    "setId": 8001,
    "setName": "售后高频问题",
    "target": "电商售后专用",
    "version": "v1.3.0",
    "total": 5,
    "passed": 4,
    "failed": 1,
    "passRate": 80,
    "avgLatencyMs": 1240,
    "runner": "超级管理员",
    "createTime": "2026-09-12 17:00:00",
    "details": [
      {
        "caseId": 8101,
        "question": "怎么退款？",
        "expected": "提交售后申请后 1-3 个工作日到账",
        "actual": "提交售后申请后 1-3 个工作日到账",
        "passed": 1,
        "score": 0.92,
        "reason": "",
        "latencyMs": 880
      }
    ]
  }
}
```
`passRate` 保留 1 位小数（前端直接拼 `%` 展示）。

## 四、权限要求

## 五、前端已完成的验证点

后端实现后可按下表逐项验证：

| # | 操作 | 预期 |
| --- | --- | --- |
| 1 | 版本与发布 → 保存为新版本 | 新版本进列表，状态为「草稿」，生效流量显示「未生效」 |
| 2 | 点「发布」拖到 20% | 状态变「灰度中」，生效流量显示 `20%` |
| 3 | 再拖到 100% | 状态变「已发布」，同 target 旧全量版本自动变「草稿」 |
| 4 | 对某版本点「回滚」 | 该版本变「已发布 / 全部」，其它在线版本降级 |
| 5 | 对生效版本点「删除」 | 按钮禁用，无法删除 |
| 6 | 点「对比」 | 默认与上一版对比，只列出有差异的配置项 |
| 7 | 点击测试「开始评测」 | 生成报告，自动跳到「历史报告」并弹出报告 |
| 8 | 报告中 `mustRefuse` 用例失败 | 失败原因显示「应拒答却给出了具体方案…」 |

## 六、暂不实现的部分（已识别，后续排期）

| 项 | 说明 |
| --- | --- |
| **提示词正文编辑器** | 当前配置仍是「参数拼装」，没有可编辑的正文。真要做需要先定正文与参数的关系 |
| **作用域与优先级** | 按 租户 / 渠道 / 业务线 分别生效，以及租户覆盖平台默认的合并规则 |
| **生成参数覆盖** | temperature / max_tokens 目前只在模型维度配，提示词维度尚未覆盖 |
| **审批流** | 发布前的人工审批链路 |
| **离线评测定时任务** | 每日自动跑一轮评测并推送通过率变化 |
| **A/B 对比报告** | 两个版本在同一评测集上的横向对比视图 |
