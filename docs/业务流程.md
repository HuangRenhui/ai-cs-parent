## 📊 核心业务流程

### 1. 用户聊天流程

```mermaid
graph TB
    A[用户] -->|发送消息| B[前端页面]
    A -.->|图片/附件<br/>选择·粘贴·拖拽| K[附件上传接口]
    K -.->|落盘 uploads/chat| L[(本地磁盘)]
    K -.->|返回元信息| B
    B -->|WebSocket| C[WebSocket 服务]
    C -->|存储消息<br/>含附件| D[基础服务]
    D -->|保存聊天记录| E[(MySQL)]
    C -->|转发请求| F[AI 代理服务]
    F -->|意图识别| G{是否需要<br/>知识库?}
    G -->|是| H[知识库服务]
    H -->|向量检索| I[(Milvus)]
    I -->|返回相似FAQ| H
    H -->|增强上下文| F
    G -->|否| F
    F -->|调用 LLM| J[LLM 服务]
    J -->|生成回复| F
    F -->|返回答案| C
    C -->|推送消息| B
    B -->|显示回复| A
```

**详细步骤**:

1. **附件上传（可选）**: 用户通过**点击选择 / 粘贴图片 / 拖拽文件**上传附件，调 `POST /file/chat-attachment`（允许全部类型，单文件 20MB），文件落本地磁盘 `uploads/chat`，返回元信息（`url` / `fileName` / `category` 等）
2. **消息接收**: 用户在前端输入消息（**可带附件，也可仅发附件不发文字**），经 WebSocket 或 HTTP 发送到后端
3. **会话管理**: 基础服务创建或更新聊天会话，存储消息记录。**附件元信息存 `cs_chat_msg.attachments`（JSON 列）**，供前端拉取历史时回显
4. **意图识别**: AI 代理服务分析用户意图，判断是否需要知识库支持
5. **知识检索**: 如需知识库，将问题向量化后在 Milvus 中检索相似 FAQ
6. **LLM 调用**: 结合上下文和知识库结果，调用 LLM 生成智能回复。**当前附件内容不参与上下文**（`parseStatus=0`，AI 读不懂附件）
7. **消息推送**: 将生成的回复通过 WebSocket 实时推送给前端

**涉及服务**:
- ai-cs-websocket (实时通信)
- ai-cs-base-service (会话管理、附件存储)
- ai-cs-agent (AI 对话)
- ai-cs-knowledge (知识检索)

**数据表**:
- cs_chat_session: 会话记录
- cs_chat_msg: 消息记录（`attachments` JSON 列存附件）
- cs_knowledge_faq: 知识库 FAQ

> **附件能力边界（A 方案）**：当前做到「上传 → 展示 → 落库回显」，**AI 尚不能理解附件内容**。
> `AttachmentDTO` 已预留 `extractedText` / `parseStatus` 字段，待模型层（`ModelRouter`）打通后
> 回填解析结果即可参与上下文拼装，无需改动 DTO 与前端。
> 平台差异：**微信小程序无剪贴板图片 API**，只能走相册/拍照入口；Web 端支持直接粘贴截图。

### 2. 工单创建流程

```mermaid
graph TB
    A[用户/坐席] -->|提交工单| B[前端页面]
    B -->|HTTP POST| C[网关]
    C -->|路由转发| D[工单服务]
    D -->|验证数据| D
    D -->|创建工单| E[(MySQL)]
    D -->|触发通知| F[消息队列/事件 ⚠️目标架构]
    F -->|分配坐席| G[坐席服务]
    G -->|WebSocket 通知| H[坐席前端]
    D -->|返回结果| C
    C -->|响应| B
    B -->|显示成功| A
```

> **注意**：消息队列（RabbitMQ/Kafka）为目标架构，**当前未接入**。工单通知直接通过 WebSocket 推送，无需经过 MQ。

**详细步骤**:

1. **工单提交**: 用户或坐席在前端填写工单信息并提交
2. **请求路由**: 网关接收请求并转发到工单服务
3. **数据验证**: 工单服务验证必填字段和业务规则
4. **持久化存储**: 将工单信息保存到数据库
5. **智能分配**: 根据工单类型和坐席负载自动分配处理人
6. **实时通知**: 通过 WebSocket 通知相关坐席有新工单
7. **结果反馈**: 返回工单 ID 和创建结果给前端

**涉及服务**:
- ai-cs-gateway (请求路由)
- ai-cs-workorder (工单管理)
- ai-cs-base-service (坐席管理)
- ai-cs-websocket (实时通知)

**数据表**:
- cs_work_order: 工单主表
- cs_agent: 坐席信息

**工单状态流转**:
```
待处理 → 处理中 → 已解决 / 已关闭
         ↓
      待跟进
```

### 3. 知识库检索流程 (RAG)

```mermaid
graph TB
    A[用户问题] --> B[前端页面]
    B -->|HTTP GET| C[网关]
    C -->|路由转发| D[知识库服务]
    D -->|文本预处理| D
    D -->|调用 Embedding| E[Embedding 服务]
    E -->|返回向量| D
    D -->|向量检索| F[(Milvus / Chroma)]
    F -->|Top-K 相似结果| D
    D -->|相似度过滤| D
    D -->|Rerank重排 ⚠️Chroma路径| D
    D -->|返回 FAQ| C
    C -->|响应| B
    B -->|展示结果| A
```

> **两条路径**：FAQ 走 **Milvus + Dashscope**（主路径）；文档 RAG 走 **Chroma + Ollama + BGE-Reranker**（可选路径）。详见 [知识库手册](知识库手册.md)。

**详细步骤**:

1. **问题接收**: 用户输入搜索问题
2. **文本预处理**: 清洗、分词、标准化处理
3. **向量化**: 调用 Embedding 服务将文本转换为向量
4. **相似度检索**: 在 Milvus 中进行向量相似度搜索
5. **结果过滤**: 根据相似度阈值过滤低质量结果
6. **排序返回**: 按相似度降序返回 Top-K 结果

**涉及服务**:
- ai-cs-knowledge (核心检索逻辑)
- 外部 Embedding 服务 (向量化)
- Milvus (向量数据库)

**关键配置**:
```yaml
embedding:
  url: http://127.0.0.1:8000/embedding
  
milvus:
  host: localhost
  port: 19530
  collection: faq_vectors
  
search:
  top-k: 5
  similarity-threshold: 0.8
```

## 🎯 典型业务场景

### 场景 1: 智能客服自动应答

**流程**:
1. 用户提问 → 2. 意图识别 → 3. 知识检索 → 4. LLM 生成 → 5. 返回答案

**适用场景**: 常见问题自动回答

### 场景 2: 人工坐席介入（✅ 已实现）

**流程**:
1. 用户要求人工 → 2. 意图识别为「转人工」→ 3. 分配坐席 → 4. 回填接待信息 → 5. 人工接待

**时序图**:

```mermaid
sequenceDiagram
    participant U as 用户
    participant C as 前端
    participant A as AiAgentService
    participant S as SessionFeign
    participant B as ChatSessionService
    participant DB as MySQL/Redis

    U->>C: 说「转人工」
    C->>A: POST /ai/chat/send
    A->>A: 意图识别 → IntentEnum.TO_AGENT
    A->>S: PUT /session/{id}/transfer
    S->>B: markTransferred(sessionId)
    B->>DB: 加 Redis 短锁（TTL 5s）
    alt 拿不到锁
        B-->>S: 抛异常（正在转接，请勿重复提交）
    end
    B->>DB: 查在线坐席（agent_status=1）
    B->>DB: 统计各坐席进行中人工会话数
    B->>B: 取「接待数最少 + ID 最小」者
    B->>DB: 更新会话（sessionType=2 + agentId）
    alt 有在线坐席
        B-->>A: agentId/agentNo/agentName 有值
        A-->>C: transferred=true + 坐席信息
        C->>C: 展示接待卡「工号 A002 张晓梅 正在为您服务」
    else 无在线坐席
        B-->>A: agentId=null，agentNo 为空串
        A-->>C: transferred=true + agentId 为空
        C->>C: 渲染排队态「正在等待人工坐席接入」
        Note over C: ⚠️ 禁止借在线坐席展示，否则等于谎称已接入
    end
    alt 调用失败
        A-->>C: transferred=false + TRANSFER_FAIL_REPLY
        C->>C: 仅显示兜底话术，不展示接待卡
    end
```

**分配策略**：只在**在线**坐席中挑选，按「当前进行中的人工会话数」升序、坐席 ID 升序取第一个。加 ID 兜底是为了结果稳定——纯按数量排序时，数量相同的坐席顺序由数据库决定。

**并发控制**：按 `sessionId` 加 Redis 短锁（TTL 5 秒）。用户连点或消息重试时，拿不到锁的请求直接失败，避免同一会话被分配给两位坐席。

**三种返回形态**（前端须区别渲染）：

| 场景 | transferred | agentId | 前端表现 |
|------|-------------|---------|---------|
| 已接入坐席 | `true` | 有值 | 接待卡展示工号姓名 |
| **无在线坐席（排队）** | `true` | **null** | **排队提示**，不展示坐席信息 |
| 转接失败 | `false` | null | 仅兜底话术，无接待卡 |

**适用场景**: 复杂问题需要人工处理

> **仍缺**：真实排队队列与排队人数/预估等待、技能组路由（现固定「综合客服」）。

### 场景 3: 知识库持续优化

**流程**:
1. 收集未解决问题 → 2. 人工标注 → 3. 添加 FAQ → 4. 向量化 → 5. 更新索引

**适用场景**: 持续提升 AI 准确率
