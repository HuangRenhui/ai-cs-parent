## 🎯 产品定义

做一个通用客服平台。电商、新零售、金融、教育、政务、医疗都用同一套内核做客服；行业差异用连接器和配置接入，不为每个行业再开发一套系统。

对照淘宝（阿里小蜜 / 千牛）、京东咚咚、亚马逊 Contact Us / Connect 的是「客服操作系统」能力（排队、坐席台、自助、工单），不是把它们的订单模型抄进内核。

**状态**：`已有` 当前代码可用 · `半成品` 有字段或演示话术 · `缺失` 尚未建模  

**成熟度**：当前仓库 = **内网演示 / POC**。未达「可售单租户」（§17-B），更未达多行业复制或 SaaS。对公网或给外部后台账号前，必须先做 §3 鉴权与 §16.1。

**原则**

1. 内核只认：租户、访客、会话、消息、队列、知识、工单、工具调用、审计、**模型调用（chat / intent / embed）**。
2. 不内置订单 / 银行卡 / 门店 / 保单等业务表。
3. 电商、新零售、金融是 **可选行业包**（预置工具名和提示词），与客户自己导入的 OpenAPI 平权。
4. 当前代码里的「查物流 / 退款」= 电商演示包，迁移前不要再往枚举里加行业意图。

> **开发提示：** 按 [§17](#17-成熟度与开发顺序照此开发) 做，不要按章节号从 1 扫到 17。B 阶段先鉴权/排队/附件/工程底线，再做 [§15](#15-傻瓜式接入任意行业零改内核待实现) 三件套。不要做内核「订单服务」。模型网关见 [§6.1](#61-大模型插拔与管理内核能力)；上线与合同见 [§16](#16-工程安全与经营商用上线必做)。约束见 [系统架构](系统架构.md)。

## 1. 目标架构（接入任意系统）

```
渠道层     Web/App SDK · 企微/微信 · 热线 · 邮件 · OpenAPI 入站
会话内核   会话 · 路由排队 · 机器人 · 坐席工作台 · 工单 · 知识库
平台层     租户 · IAM · 审计 · 质检 · 报表 · 工作流 · **模型网关**
开放层     OpenAPI · Webhook · Tool SPI · 卡片协议 · 身份映射
连接器     REST / gRPC / MQ / 数据库只读
行业包     电商 OMS · 新零售 CRM/POS · 金融核心/KYC · 自定义 OpenAPI
```

接入方系统只做三件事：

1. **身份**：把己方用户 ID 映射成客服侧 `visitorRef`（可匿名，登录后合并）。
2. **上下文**：打开聊窗时传入 `scene` + `entities[]`（如 `{type:order, id:…}` 或 `{type:account, id:…}`）。
3. **工具**：注册可被机器人/坐席调用的查询与动作（查单、退款、冻卡、改预约），由连接器转发到对方系统。

客服内核只认：访客、会话、消息、队列、知识、工单、工具调用记录、模型调用。不认「订单表」。

### 1.1 开放契约（应实现的 SPI）

| 契约 | 用途 | 状态 |
|------|------|------|
| Widget / SDK 初始化 | `tenantId, channel, visitorRef, scene, entities, locale` | 已有（`POST /open/widget/init` + `/widget`；场景化开场白/快捷动作见 `cs_scene_config`） |
| 身份映射 | 外部用户 ↔ 内部客户，支持合并匿名会话 | 半成品（`cs_visitor_map`） |
| Tool Registry | 工具名、JSON Schema、权限、超时、幂等键 | 半成品（`cs_open_tool`，LLM Function Call 未全接通） |
| Connector | REST/gRPC/MQ、鉴权、字段映射、沙箱 | 半成品（MOCK + REST） |
| 入站 Webhook | 对方系统推送物流变更、退款结果、工单进展 | 缺失 |
| 出站 Webhook | 会话开始/转人工/结束/评价，供对方 CRM 订阅 | 缺失 |
| 行业包开关 | 启停 / 仅启用此包，关闭后工具立即不可用 | 半成品（`cs_open_pack` + `/open`） |
| 模型网关 | 供应商适配、按任务路由、管理页开关（见 6.1） | 半成品（登记/生效/探活/故障转移已有；按意图细分绑定仍缺） |
| 卡片协议 | 通用「实体卡 / 按钮 / 表单」，由行业包渲染 | 缺失 |
| OpenAPI 导入 | 贴 Swagger 自动出工具列表 | 缺失 |
| 连接器字段映射 | 对方 `orderNo` ↔ `entity.id`，鉴权向导 + 测通 | 缺失 |
| 行业提示词包 | 开包加载人设 / 拒答 / 槽位，不写死电商 | 缺失 |
| 工具幂等 | `idempotencyKey` 防重复退款/冻卡 | 半成品（调用表落键，相同键回放首次成功） |
| 连接器 SSRF 防护 | 禁止打内网/元数据地址；URL 白名单 | 半成品（禁内网/元数据/环回；尚无租户出站白名单） |
| OpenAPI + 签名 | 第三方自建渠道、自建机器人、自建报表 | 缺失 |

商用验收：同一套内核，换电商连接器能查单退款；换金融连接器能查账冻卡；不改会话与坐席代码。实施方按 [§15](#15-傻瓜式接入任意行业零改内核待实现) 向导配置即可，不必改 Java。

## 3. 平台底座（所有行业都要）

对标：亚马逊 Connect 的实例/路由配置；淘宝/京东的商家后台权限与审计。

| 功能 | 说明 | 对照 | 状态 | 优先级 |
|------|------|------|------|--------|
| 多租户 | 租户/品牌/门店隔离数据与坐席 | 淘宝一店一队；Connect Instance | 缺失 | P0 |
| 登录 | 账号密码 + SSO（OIDC/SAML/LDAP） | 千牛/咚咚登录 | 半成品（账号密码 + JWT；无 SSO） | P0 |
| 密码安全 | 哈希、锁定、过期、MFA（金融建议强制） | 金融合规 | 半成品（BCrypt；无锁定/过期/MFA） | P0 |
| RBAC | 超管、租户管理员、班长、坐席、只读质检 | 角色分权 | 半成品（用户/角色/菜单；无技能组数据权限） | P0 |
| 数据权限 | 只能看本技能组/本店会话 | 店铺隔离 | 缺失 | P0 |
| 操作审计 | 谁改了知识、谁退了款、谁导出了聊天 | 金融/电商风控 | 缺失 | P0 |
| 敏感信息脱敏 | 手机、证件、卡号在日志与坐席屏打码 | PCI / 个保法 | 缺失 | P0 |
| 限流熔断 | 网关限流、机器人配额、工具调用配额 | 防刷单/防撞库 | 半成品（网关 RedisRateLimiter Bean，路由未挂载） | P0 |
| 分页与检索 | 会话/客户/工单/FAQ 分页、时间范围 | 生产数据量 | 半成品（仅 FAQ 分页） | P0 |
| 配置与密钥 | 分环境、密钥不进仓库、连接器密钥加密 | 商用部署 | 半成品 | P0 |
| HTTP/WS 鉴权 | 后台 JWT/Session；**WebSocket 必须带 token**，禁止只靠猜 sessionId | 防会话劫持 | 半成品（HTTP JWT + WS `?token=`；网关 `/ws/` 仍白名单，由端点校验） | P0 |
| HTTPS / 安全头 | 生产强制 TLS；CORS 收紧到业务域名（当前网关过宽） | 浏览器与等保 | 缺失 | P0 |
| 依赖治理 | 迁出 Fastjson 1.2.83（已知风险）→ fastjson2 或 Jackson | 安全扫描 | 缺失 | P0 |
| 可观测 | 结构化日志、requestId、全链路、告警（见 [§16.4](#164-日志排障与全链路运维)） | 值班排障 | 半成品（JSON 行日志 + X-Request-Id + `/ops/logs`；无 OTel） | P0 |
| 操作日志 | 后台操作写入 `cs_operation_log` 并可查询 | 审计基础 | 半成品（有表与查询；知识改删/退款导出仍缺） | P0 |
| 网关请求日志 | 记录路径、方法、耗时 | 排障 | 已有 | P1 |
| 下游用户头 | 网关注入 `X-User-Id` / `X-Username` | 服务识别调用方 | 已有 | P1 |

### 6.1 大模型插拔与管理（内核能力）

和行业包同一类：**后台登记 + 开关 + 运行时按规则选用**。这是内核能力（与知识库、会话同级），不绑某个行业包，也不按厂商拆微服务。实现细节见 [AI模型统一管理](AI模型统一管理.md)。

当前：对话/向量经 `ModelRouter`（OpenAI 兼容协议）。未在 `cs_ai_model` 登记时回退 `ai.llm` / `ai.embedding`（`DashscopeModelClient`）。提示词仍集中在 `PromptConst`。换协议只改适配器，不要再写第二套 HTTP 客户端。

#### 分层

```
管理页：供应商 / 模型 / 密钥 / 默认 / 备用 / 探活
        ↓
路由：按任务选模型（意图识别、咨询生成、工具调用、Embedding……）
        ↓
LLM 网关（Adapter）：通义 · OpenAI 兼容 · Azure · 本地
        ↓
主模型失败 → 备用；全挂了才用「系统繁忙」话术
```

内核只认三种调用：`chat`（对话生成）、`intent`（意图/分类）、`embed`（向量）。不认某个厂商的 URL 和报文。

#### 管理页（运营后台 `/ai-model`）

做成「开放接入」那种配置页，**不要**做成会话中搜模型的下拉。C 端 Widget 不出现选模型。

| 配置项 | 说明 | 状态 |
|--------|------|------|
| 供应商 | 协议（通义 / OpenAI 兼容 / 本地 Ollama）、地址 | 半成品（Azure 未做） |
| 密钥 | 只存后端、AES-GCM 加密；回显脱敏；不进会话 JSON | 已有 |
| 模型 | 名称、能力标签（对话 / 向量等）、温度、维度、超时、熔断阈值、输入/输出单价 | 已有（`cs_ai_model`） |
| 开关 | 启用、停用、设为默认（同能力仅一条生效） | 已有 |
| 按任务绑定 | 意图识别→便宜快；咨询生成→质量；工具调用→须支持 Function Call；Embedding→专用向量模型 | 半成品（按能力类型，意图与生成共用 LLM） |
| 备用链 | 超时/失败按 priority 自动切备用 | 已有 |
| 探活 | 「测试连接」；连续失败达阈值自动熔断，冷却 60s 探测恢复 | 已有 |

坐席工作台最多只读「当前：通义 qwen-turbo」，或给主管会话级覆盖。**C 端 Widget 不出现选模型。**

#### 约束（后面补代码时不要违反）

- 一个 `LlmGateway` + 若干 Adapter，不要每个厂商一个微服务
- 不要和行业包绑死（「金融包必须用某云」会把内核写死）
- 不要让一线坐席或顾客每条消息自己挑模型（成本、合规、口径会乱）
- High / Fast / Max 不是产品核心；客服要超时、限流、日成本上限、是否出域
- 知识库 Embedding 与对话模型分开登记，不要共用一个 `model` 字段对付所有调用

#### 后续补齐

1. 意图识别与咨询生成拆开绑定  
2. 费用与失败看板  
3. Azure Adapter（若合同需要）  

优先级低于登录鉴权、技能组排队、工具 JSON Schema 交给模型选；高于「再写一套某某云 SDK」。

## 15. 傻瓜式接入（任意行业零改内核，待实现）

目标：对方实施只走管理页向导，**不读模块说明、不改 `IntentEnum`、不发版**。会话 / 知识 / 工单骨架已经通用，不要再做成行业分叉。卡住「换行业就要改代码」的是意图、提示词、工具怎么选、连接器怎么配、C 端怎么嵌。

已通用、实现时不要改坏：会话消息、客户档案、坐席状态、工单主表、FAQ+RAG、`entities[{type,id}]`、行业包开关、连接器/工具表、`/widget`。不要加 `orderId` / 银行卡 / 门店表。

### 15.1 实施方只做这一页（产品向导）

1. 开租户（账号 + 密钥）  
2. 选行业包或「自定义」（提示词、示例工具一起带上）  
3. 配连接器（URL、鉴权、测通）或导入 OpenAPI  
4. 嵌一行 SDK（`visitorRef` + `entities`，无实体也能开）；入口可带 `scene`（订单/产品/售后），开场白与快捷动作按 `cs_scene_config` 配置，已在「开放接入」页可视化维护  
5. 导入知识库  
6. （可选）填 Webhook  

验收：换电商连接器能查单退款，换金融连接器能查账；**不改会话和坐席代码**。

### 15.2 不改就无法「任意行业零开发」

| 项 | 现状 | 傻瓜式目标 | 状态 | 优先级 |
|----|------|------------|------|--------|
| 意图去枚举 | `IntentEnum` + `switch` 写死查物流/退款；`fromName` 用「物流、退款」模糊匹配 | 内核只留：咨询（RAG）、投诉（建单）、转人工、**调用已注册工具**。`intentBind` 仅作电商包默认绑定 | 缺失 | P0 |
| 提示词跟包走 | `PromptConst` / Widget 欢迎语自称电商、追问订单号 | 开包加载人设、拒答、槽位；内核只留「只输出 JSON / 不编造 / 不足转人工」 | 缺失 | P0 |
| 连接器向导 | REST 仅 `baseUrl+httpPath`，鉴权是一段 JSON | 三步：贴地址和密钥 → 勾选接口（可导入 OpenAPI）→ 测通启用；字段映射对方 `orderNo`↔`entity.id`；沙箱/生产两套地址 | 缺失 | P0 |
| 工具由模型选 | 意图名 == `intentBind` 才调用；`input_schema` 未交给 LLM | Function Call 看已启用包的工具描述；`write`/`critical` 只出确认卡 | 半成品 | P0 |
| 一行 C 端 SDK | `/widget` 要拼 query，欢迎语带电商词 | `<script src=sdk.js>` + `CS.open({tenant, visitorRef, scene, entities})`；卡片数据由连接器填 | 半成品 | P1 |
| 出入站 Webhook | 只能客服去拉 | 固定事件目录 + 签名；对方推实体状态变化，聊窗出系统消息或刷新卡片 | 缺失 | P1 |
| 工具幂等 + 高风险确认 | `risk=write` 演示仍可真下 | 写操作必须幂等键；critical 只出确认卡 | 缺失 | P0 |
| 连接器安全 | `auth_json` 明文；REST 可指内网 | 密钥加密；SSRF 白名单；超时/重试/熔断 | 缺失 | P0 |

当前最不像通用平台的三处：**`IntentEnum` + 电商提示词 + 用意图名绑工具`**。开放表形状已对，运行时仍走电商枚举。

**实现时建议先做这三件**（换行业不用发版 + 对方可自己对接）：

1. 意图去枚举化  
2. 提示词 / 欢迎语跟行业包走  
3. 连接器向导：导入 OpenAPI + 测通 + 字段映射  

模型网关（§6.1）和独立 SDK 紧随其后。

### 15.3 不挡换行业、但卖给第二家必须做

| 缺口 | 说明 | 清单位置 |
|------|------|----------|
| 多租户 | 一家一套数据，不能一键开实例 | §3 |
| 登录 + RBAC | JWT + RBAC 已有；无 SSO、锁定、租户隔离登录 | §3 |
| 知识按租户隔离 | `tenant_code` + Milvus 过滤已有；登录未按租户隔离 | §7 |
| 工单类型与自定义字段可配 | 后台写死「退款」选项 | §8 |
| 客户扩展字段 | 会员等级、网点不要加死列 | §10 |
| 模型管理页 | 每家 LLM 不同，现在改 yml | §6.1 |

排队与坐席台是人机协同产品，和「接对方 OMS」分开做。

### 16.4 日志、排障与全链路（运维）

目标：线上出问题，运维能用 **一个 ID** 把「用户一句话 → 网关 → WS/AI → 开放层/知识库/工单」整段捞出来，看失败点和耗时。当前做不到。

**现状：** 各服务 JSON 行日志 + MDC `requestId`；网关生成 `X-Request-Id` 并下传；Feign 透传；前端 Axios 带 ID；`ai-cs-ops` 可读本地 `logs/`。尚无 Loki/ELK、无 Micrometer Tracing / Zipkin。`cs_open_tool_invoke` 可复盘工具调用。

运维检索主键（实现时必须进 MDC / 日志字段）：`traceId`、`requestId`、`sessionId`、`tenantId`、`visitorRef`、服务名。

```
浏览器 / 坐席台
    │  X-Request-Id（无则网关生成）
    ▼
网关 ──► WS / AI ──► 开放层 · 知识库 · 工单 · 基础服务
    │
    └─ 同一 traceId 写入日志 ──► 日志平台（按 sessionId / traceId 搜）
                              └─ 可选 Zipkin / SkyWalking 看调用图与耗时
```

#### 第一层：能复盘（B 阶段必做，P0）

| 项 | 说明 | 状态 |
|----|------|------|
| 统一 JSON 日志 | 时间、级别、服务名、`traceId`、`requestId`、`sessionId`、`tenantId`、logger、消息 | 半成品 |
| 网关生成 ID | 无则生成 `X-Request-Id`；响应头回传，方便前端/抓包对照 | 已有 |
| 跨服务传递 | Feign、WebSocket、RestTemplate 把 requestId/traceId 往下传并写入 MDC | 半成品（Feign + HTTP Filter + WS query） |
| 前端带 ID | Axios / WS 带上或回显 `X-Request-Id`，坐席报障时能报这个号 | 半成品 |
| 文件滚动 | 各服务 `logs/{app}.log`，按日/大小切割，保留天数可配 | 已有 |
| 采集检索 | Filebeat→ELK 或 Promtail→Loki；**按 sessionId / requestId 一条语句查出全路径** | 缺失 |
| 日志脱敏 | 禁止打手机号、证件、卡号、API Key、完整模型报文、连接器 auth | 缺失 |

没有采集平台时，至少保证单机 `logs/` 格式统一、能 `grep requestId`。多实例必须集中收集，禁止 SSH 逐台翻。

#### 第二层：全链路追踪（C 阶段，P1）

| 项 | 说明 | 状态 |
|----|------|------|
| 追踪 SDK | Spring Boot 3 用 **Micrometer Tracing + OpenTelemetry**（不要用已停更的 Sleuth） | 缺失 |
| 导出后端 | Zipkin 或 SkyWalking（二选一即可，不要两套） | 缺失 |
| 埋点范围 | HTTP、Gateway、Feign、WS、MySQL、Redis、对外 LLM/REST 连接器 | 缺失 |
| 与日志同源 | span 的 traceId **等于** 日志里的 traceId，复盘一边搜日志、一边看调用图 | 缺失 |
| 慢调用 | P95/P99、LLM 超时、工具失败在图上可点 | 缺失 |

#### 第三层：值班告警（C 阶段，P1）

| 项 | 说明 | 状态 |
|----|------|------|
| Actuator | `/actuator/health`、`/ready`；生产收紧暴露面 | 半成品（网关已配；生产暴露面未收紧） |
| 黄金指标 | 请求量、错误率、延迟、饱和度（按服务） | 缺失 |
| 业务告警 | LLM 连续失败、工具失败率、WS 断开、队列堆积 | 缺失 |
| 审计与技术日志分离 | 登录/改知识/write 工具进审计表；排障看日志+trace，合规看审计 | 半成品（仅工具调用表） |

#### 约束（实现时不要违反）

- 不自研 APM；用 OTel 标准，便于私有化客户自带平台  
- 日志与追踪是运维能力，不按行业包拆  
- WebSocket 无进程内状态可查，排障必须靠日志/trace 头  
- 技术日志保留天数与合规「操作审计留存」分开配置（见 16.3）  

#### 建议落地顺序

1. 公共 logback JSON + 网关/Feign/WS 传 `X-Request-Id` + MDC（当天就能 grep 复盘）  
2. 文件滚动；有条件再接 Loki/ELK  
3. Actuator health/ready  
4. Micrometer Tracing → Zipkin 或 SkyWalking  
5. 告警规则  
6. **运维控制台模块**（§16.5）：后台可查日志与链路，不必 SSH  

### 16.5 运维控制台模块（`ai-cs-ops`）

把「看服务、查日志、看链路、看告警」收成 **独立内核模块**，不要散落在各业务服务里，也不要让运维去翻 Kibana/Zipkin 原生地址（私有化客户往往不给）。一线坐席 **不进** 本模块。

| | 约定 |
|--|------|
| 后端 | 新模块 `ai-cs-ops`，建议端口 **8087**，网关 `/ops/**` |
| 前端 | 运营后台菜单「运维」，路由 `/ops`、`/ops/logs`、`/ops/traces`、`/ops/alerts`（`meta.roles` 仅超管/运维） |
| 数据 | 读日志后端（Loki/ES）与追踪后端（Zipkin/SkyWalking）的 **查询适配器**；本模块不存业务会话，可存告警规则与查询审计 |
| 权限 | RBAC：`OPS_VIEW` / `OPS_ADMIN`；查询操作写审计（谁搜了哪个 sessionId） |

与 §16.4 关系：16.4 是采集与标准；**16.5 是给人用的页面**。没有 16.4 第一层，页面只能空壳。

#### 页面与接口

| 页面 | 路径 | 能力 | 状态 |
|------|------|------|------|
| 运维总览 | `/ops` | 各服务存活、近 1h 错误率/延迟、LLM/工具失败数、未恢复告警 | 半成品（存活 + 本地错误条数 + 临时告警） |
| 日志查询 | `/ops/logs` | 按 `requestId` / `traceId` / `sessionId` / `tenantId` / 服务 / 级别 / 时间；一条请求的时间线 | 半成品（读本地 `logs/`） |
| 链路追踪 | `/ops/traces` | 按 traceId 或 sessionId 打开 span 瀑布图；点 span 跳转同行日志 | 半成品（按日志 traceId 聚合，未接 Zipkin） |
| 告警 | `/ops/alerts` | 规则列表、当前告警、静默；通道（邮件/企微，可后做） | 半成品（内存规则 + 健康探测事件） |
| 服务健康 | `/ops/health` | 聚合各服务 Actuator health/ready，禁止把管理端口直接暴露公网 | 半成品（HTTP 端口探测，未接 Actuator） |

建议 API（均经网关，须登录）：

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/ops/overview` | 总览卡片 |
| GET | `/ops/health` | 服务健康列表 |
| GET | `/ops/logs` | 日志检索（分页，脱敏后返回） |
| GET | `/ops/logs/{requestId}` | 同一 requestId 全服务日志 |
| GET | `/ops/traces` | 链路列表 |
| GET | `/ops/traces/{traceId}` | span 树 |
| GET/PUT | `/ops/alerts` | 告警规则与事件 |

第一期无 Loki/Zipkin 时：`ai-cs-ops` 可读各节点约定目录的滚动日志（仅单机/POC），接口形状不变；接上采集平台后只换适配器，**不要改前端**。

#### 约束

- 返回前端的日志必须已脱敏（16.4）  
- 禁止在页面展示 API Key、模型全文、连接器 auth  
- 不自研存储海量日志；ES/Loki/Zipkin 是后端，ops 是门面  
- 不按行业包拆运维台；租户隔离后运维默认可看本租户，平台超管可看全部  
- `ai-cs-job` 仍负责任务，不负责本控制台  

#### 落地顺序

1. 模块骨架 + 网关路由 + 前端空菜单（需先有登录，否则只内网）  
2. 对接 16.4 第一层：日志查询页（requestId/sessionId）  
3. 总览 + health 聚合  
4. 对接 Zipkin/SkyWalking：链路页  
5. 告警页  

B 阶段至少要有 **日志查询页**（可先读本地文件）。C 阶段补齐链路与告警。

## 20. 技术改造计划

不挡 §17-B。未出现明确性能或安全瓶颈前，优先鉴权、排队、会话附件与工程底线。

### 20.1 WebSocket 替换为 Netty 改造方案

#### 20.1.1 现状分析
- **当前实现**: Spring WebSocket (JSR-356)，模块 `ai-cs-websocket`，端口 **8081**
- **优点**:
  - 与 Spring Boot 无缝集成
  - 开发简单，维护成本低
  - 满足当前演示 / POC 业务需求
- **缺点**:
  - 同步阻塞 IO，并发能力有限
  - 内存占用较高
  - 连接在进程内存，未水平扩展
  - 扩展性受限于 Servlet 容器

#### 20.1.2 Netty 改造可行性评估

**改造优势**:
- **高性能**: 异步非阻塞 IO，单机可支持数十万并发连接
- **低延迟**: 零拷贝技术，减少数据复制开销
- **资源节省**: 更少的线程消耗，降低内存占用
- **协议灵活**: 支持自定义协议，易于扩展
- **稳定性**: 经过大量生产环境验证

**改造挑战**:
- **开发成本**: 需要重写整个 WebSocket 模块（预计 2–3 周）
- **学习曲线**: 团队需要掌握 Netty 框架
- **Spring 集成**: 需要手动处理依赖注入、事务等
- **测试工作量**: 需要全面的压力测试和稳定性测试
- **运维复杂度**: 监控、日志、异常处理需要重新设计
- **会话鉴权**: 现行须带 `?token=`，替换后鉴权与心跳不能回退成猜 sessionId

**决策建议**:

| 场景 | 建议 | 理由 |
|------|------|------|
| 当前用户量 < 1 万并发 | 不建议改造 | Spring WebSocket 已足够，ROI 低 |
| 用户量 1–10 万并发 | 谨慎评估 | 可先优化现有代码，观察性能瓶颈 |
| 用户量 > 10 万并发 | 推荐改造 | Netty 优势明显，值得投入 |
| 有长期高并发规划 | 提前布局 | 作为技术储备，分阶段实施 |

#### 20.1.4 技术选型对比

| 特性 | Spring WebSocket | Netty |
|------|------------------|-------|
| 并发能力 | 中等（千～万级） | 高（十万级） |
| 开发难度 | 低 | 中高 |
| 维护成本 | 低 | 中 |
| 性能 | 良好 | 优秀 |
| 生态集成 | 优秀（与 Spring Boot 一体） | 需手动集成 |
| 适用场景 | 中小规模 / 当前 POC | 大规模高并发 |

#### 20.1.5 风险评估与应对

| 风险 | 影响程度 | 应对措施 |
|------|----------|----------|
| 开发延期 | 中 | 预留缓冲时间，分里程碑验收 |
| 兼容性问题 | 高 | 充分的测试覆盖，灰度发布 |
| 性能不达预期 | 中 | 压测验证，保留回滚方案 |
| 团队技能不足 | 中 | 提前培训，引入外部专家 |
| 线上故障 | 高 | 完善监控告警，快速响应机制 |
| 鉴权回退 | 高 | 禁止只靠猜 sessionId；WS 必须带 token |

#### 20.1.6 成本估算

- **人力成本**: 1 名高级开发 × 6–8 周 = 6–8 人周
- **测试成本**: 1 名测试 × 2–3 周 = 2–3 人周
- **风险成本**: 预留 20% buffer
- **总计**: 约 10–13 人周

**最终建议**:
当前仓库处于内网演示 / POC，建议优先验证业务模型和完成 §17-B。除非遇到明确的性能瓶颈或有明确的高并发需求，否则暂不进行 Netty 改造。可将本方案作为技术储备，待业务发展到一定规模后再行评估。

- **Spring WebSocket**（当前）

## 23. 注意事项

1. **向后兼容**：接口与表结构变更走迁移脚本，不破坏现有会话与工单。
2. **多媒体性能**：图片/音频处理与向量化是计算密集任务，上传走异步或限流，避免拖垮对话接口。
3. **存储成本**：知识库媒体与会话附件分开规划；生产附件进对象存储，本地盘仅开发。
4. **上传安全**：校验魔数，不只信 Content-Type；压缩包防 Zip 炸弹与 Zip Slip。
5. **用户体验**：大文件进度与断点续传针对知识库文件；会话气泡富媒体仍见第 9 节。
6. **扩展性**：行业差异走连接器与配置，不把订单/银行卡/门店写进内核。
7. **状态诚实**：以上文表格为准，演示/POC ≠ 可售闭环。
8. **端口**：网关到 job 为 **8080–8088**。
