## 0. 怎么用这份清单

**当前的定位**：`ai-cs-knowledge` 的 FAQ 检索链路（向量化 → 检索 → 生成 → 三态返回）是**正确的骨架 + 交付级实现**，
不是生产级实现。判断标准取决于目标：

| 目标 | 结论 |
|------|------|
| 几十租户的交付 / 演示 / 内网部署 | **可交付**。一致性与失败语义这块已按生产思路设计 |
| 对外 SaaS、多租户千级、高并发、要算成本 | **需补齐 P1 + P2**，其中规模假设（集合数）与成本控制（重复 embedding 付费）是硬门槛 |

每条差距统一按「**现象 → 为什么是问题 → 建议做法 → 依赖**」写，便于直接转成任务。

## 1. 已达到生产思路的部分（保留，勿回退）

| 做法 | 价值 |
|------|------|
| 外部系统不进本地事务：先落库、再调 embedding / 向量库 | 避免跨系统长事务；失败只降级为「已落库、向量化待补」 |
| DB 为权威源、向量为派生索引；检索**按 faqId 回查 DB** 二次校验 | 防脏数据答出（过滤已删 / 未发布），兜住 fail-open 遗留的孤儿向量 |
| 三态失败语义（HIT / MISS / UNAVAILABLE）+「不假装成功」约定 | 上层能区分「没查到」与「服务挂了」，降级话术不同 |
| 删除向量 fail-open + Redis 待清理登记 + 对账任务补偿 | 典型「最终一致 + 补偿」模型；记为 `业务类型:租户:id` |
| 按业务主键（faqId / chunkId）幂等 upsert | 重试、重放、重复执行安全 |
| 占位登记 + 文档与代码同步 | 联调与验收可依赖 |

## 3. P1：建议近期补齐

### 3.1 向量状态与内容指纹（防重复付费）

- **现象**：`cs_knowledge_faq` 没有 `vector_state` / `content_hash`；「哪些没入向量」只能反查向量库（`/knowledge/vectorize/status` 每翻一页打一次 Milvus），且**内容没变也会重新调 embedding**。
- **为什么是问题**：embedding 是**按量计费**的；管理页重复点「向量化」、批量全量重算都在重复花钱；反查向量库的成本随分页放大。
- **建议做法**：业务表加 `vector_state`（0 待入 / 1 已入 / 2 失败）、`vector_synced_at`、`content_hash`（分类+问+答 的 SHA-256）；写入/更新时比较 `content_hash`，不一致才调 embedding；用「扫描 `vector_state != 1`」替代反查 Milvus；保留 `/vectorize/status` 作兜底。
- **依赖**：无（可先做 FAQ，切片同理）。

### 3.2 批量向量化并发 + 限流

- **现象**：`batchVectorizeAndInsert` 是 `for` 循环**串行逐条**调用 embedding。
- **为什么是问题**：`/knowledge/vectorize/batch` 对 200 条 FAQ 会非常慢（每条一次 HTTP），且易触发供应商限流。
- **建议做法**：线程池（有界队列 + 超时）并发，失败单条不影响整体；对 embedding 调用加**令牌桶限流**；供应商支持 batch 接口时一次多条（最省钱）。
- **依赖**：`ModelRouter` 需暴露并发友好的入口。

### 3.3 缓存（答案级 + embedding 级）

- **现象**：同一问题重复打 embedding + LLM，无任何缓存。
- **建议做法**：先用**问题归一化缓存**（Redis，key=租户+归一化问题，TTL 短）；进阶做语义缓存（问题向量近邻命中即复用答案，注意租户隔离与知识更新失效）；知识变更时按租户失效。

### 3.4 接入内容安全与提示词注入防护

- **现象**：`common` 里已有 `ContentSafetyChecker`、`PromptInjectionProtection`，但 `ai-cs-knowledge` **0 处引用**。
- **建议做法**：检索入口（帮助中心匿名接口尤其）做注入检测；`industryPrompt` 与用户问题入 prompt 前做长度与注入校验；输出侧做内容安全校验。

### 3.5 可观测性（trace + 指标 + 告警）

- **现象**：这条链路**无 traceId / MDC**、无指标（QPS、命中率、P95 延迟、embedding 与 token 成本）、无告警。
- **建议做法**：接入统一 traceId（网关生成 → Feign 透传 → 日志 MDC）；埋点：检索命中率、MISS/UNAVAILABLE 比例、embedding 调用量与耗时、LLM token 与费用、向量库连接状态；对「UNAVAILABLE 突增」「集合创建失败」设告警。

### 3.6 重试退避与超时治理

- **现象**：`ModelRouter` 重试**无退避**（已核实无 sleep/backoff），失败立即重试下一候选。
- **建议做法**：指数退避 + 随机抖动；按错误类型区分（429 / 5xx / 超时）决定是否重试与切候选；为检索链路设整体超时预算。

### 3.7 匿名接口限流与防刷

- **现象**：`/help-center/**` 是网关白名单匿名接口，检索与浏览**无限流**。
- **建议做法**：按 IP / 设备指纹限流（检索与 view 分开配额）、异常流量识别、必要时加验证码；`view` 计数防刷（同 IP 短时间只计一次）。

### 3.8 分级降级

- **现象**：任一环失败即 `UNAVAILABLE`（向量库挂了整条链路不可用）。
- **建议做法**：向量不可用时退化为 DB 关键词检索（`question/answer LIKE`）+ 兜底话术；LLM 不可用时返回命中 FAQ 原文（并标注「当前为原文」）。

## 4. P2：随规模推进

### 4.1 租户隔离升级（集合数上限）

- **现象**：一租户一 Milvus collection，集合数随租户线性增长。
- **为什么是问题**：Milvus 的 collection 有元数据 / 内存 / load 开销，**上千租户**时不可持续。
- **建议做法**：改用 **partition key**（按 `tenant_id` 分区，官方推荐）或单集合 + 强过滤；或按租户分库（大客户独立实例）。无论哪种，都要**监控集合数**并设上限告警；迁移需要一次性重建。

### 4.2 索引与阈值参数化、离线评测驱动

- **现象**：IVF_FLAT + `nlist=128` + `nprobe=16` + 阈值 `0.40` 是初始值；「效果评测」页面目前返回固定 ~75% 的假报告。
- **建议做法**：按数据量调 `nlist`（≈√n），或直接用 HNSW / AutoIndex 并比较召回与延迟；**阈值由离线评测集标定**（先落地 `PromptEvalController` 的真实跑批），模型或语料变化后重新标定。

### 4.3 混合检索与重排

- **现象**：只有单路向量召回，无 BM25、无 rerank、无查询改写；`RetrievalOptimizerService`（质量过滤 / BM25 / 上下文压缩）仍是占位且被刻意绕开。
- **建议做法**：落地 `RetrievalOptimizerService`（先做上下文压缩与条数限制）→ 加 BM25 关键词召回 → RRF/加权融合 → rerank 模型；查询改写（同义扩展 / HyDE）按效果决定。

### 4.4 配置热更新与向量重建工具

- **现象**：`milvus.*` 只读 yml（Nacos 已在用但未接）；换向量模型「需重建集合」但**没有重建工具**。
- **建议做法**：向量库配置走配置中心并支持热切换；提供 `drop/rebuild` 运维接口或任务（按租户重建 + 进度上报 + 失败重试），换模型时一键重建。

### 4.5 灰度与版本化

- **现象**：提示词 / 模型变更无版本灰度（提示词版本与发布功能本身是内存桩）。
- **建议做法**：落地提示词版本（草稿 / 灰度 / 回滚）与「按会话一致性哈希分流」；模型切换同样按租户/比例灰度，异常自动回退。

### 4.6 测试体系

- **现象**：本轮新增代码**无单测**；无中间件集成测试。
- **建议做法**：核心逻辑单测（阈值过滤、三态映射、租户归一化、引数组装）；Testcontainers 起 MySQL / Redis / Milvus 做集成测试；把「向量化 → 检索 → 生成」串成端到端用例。

### 4.7 成本与配额治理

- **现象**：用量已计量（`ModelUsageRecorder` → Redis 流），但 job 侧消费落库仍占位；租户配额只有日配额保护。
- **建议做法**：落地用量落库与看板（按租户 / 模型 / 能力维度），把 embedding、LLM token、rerank 分别计量；超额限流或降级，支持按租户配额调整。

### 4.8 数据合规

- **现象**：FAQ / 文档切片可能含 PII；日志已脱敏但存储与导出未做识别。
- **建议做法**：入库前 PII 识别与可选脱敏；未命中问题表设置留存期限（`DataRetentionService` 已有雏形）；导出与查看操作进审计。
