后端**已提供接口壳、但尚未真正落地**的能力汇总。用于前端联调、排期与验收时确认「哪些功能看着能用、实际还没做完」。

**排期先看 [§2.2 优先级排序](#22-优先级排序建议实现顺序)**：已按 P0–P3 分级（共 38 项，序 1–38 即建议实施顺序），并给出「五步推进」建议与依赖关系。

## 1. 三种占位风格

| 风格 | 返回类型 | 特征 | 适用 | 前端表现 |
|------|---------|------|------|---------|
| **空结构** | `Result<Map<String, Object>>` | `LinkedHashMap` 组结构，**最后一个 key 固定为 `implemented=false`**；`Result.success(...)` 而非 `fail`，保留 `code=200` | 查询类（GET） | 读到 `implemented=false` → 显示「后端未完成」警示横幅 |
| **纯文案** | `Result<String>` | 返回「已接收（后端暂未实现持久化）」这类明确文案，**不带 `implemented`** | 写操作（POST/PUT/DELETE） | 提示成功但数据不持久化，刷新即丢 |
| **内部方法桩** | `boolean` / 对象 / `void` | 返回 `null`、空集合、`false` 或空方法体，**不经 `Result` 包装** | Service 内部方法、被 Feign 调用的服务（非 HTTP 接口） | 前端**看不到**占位标记，只能从行为反推 → 必须在本文逐条登记（见 §2.1） |

三种风格都配 `log.info("[占位] ...")`（鉴权类用 `log.warn`）记录请求，便于确认「请求确实到了后端但没落库」。

> **为什么保留 `code=200`**：前端要读到 `implemented=false` 才能显示横幅。若直接返回 4xx/5xx，前端只会弹一个泛化的错误提示，看不出「是没实现」还是「真的坏了」。这条理由只对前两种风格成立；**内部方法桩不经过 HTTP 响应**，前端无法据此显示横幅，所以第三种必须在 §2.1 登记清楚。

### 1.1 ⚠️ 安全约定：未实现的鉴权一律失败关闭

鉴权类占位（如 `WebhookService.validateInboundWebhookAuth`）**必须返回 `false`（fail-closed）**，绝不默认放行；补实现时保持同样的失败关闭语义。

后果要写清：该占位恒 `false` 会让入站 Webhook 回调**一律 401**。这不是「功能没做完」，而是**主动拒绝**——性质与返回空数据的占位不同，联调时别当成 bug。

### 2.2 优先级排序（建议实现顺序）

**排序依据**（按权重从上到下）：

1. **阻塞真实可用闭环** —— 前端已有页面/入口，但流程走不通
2. **公共底座优先** —— 被多个能力共用的底层（LLM 层、向量与检索、RBAC 种子）先补，否则上层补了也是空转
3. **真实对接前置** —— 不补就无法接外部系统（而非仅影响演示）
4. **安全** —— 已失败关闭，或存在绕过风险
5. **演示卖点** —— 对外讲得响的能力
6. **依赖关系** —— 被其它未完成项阻塞的往后排
7. **失败关闭可延后** —— 「主动拒绝」型占位（如入站验签恒 401）不影响演示安全，可并入对接阶段

> 分级口径（与 [项目现状](项目现状.md) 的 P0/P1/P2 一致，本文另拆出 P3 承接可选增强）：
> **P0** = 可售最小闭环仍缺 · **P1** = 真实对接与对外集成 · **P2** = 功能完整性 · **P3** = 可选 / 低频增强。
> P1/P2/P3 内部按「底座 → 页面 → 增强」排序，序 1–38 为全局建议实施顺序。

| 后端有、前端未接入 | 4（逐条核实后均非缺口，见下） |

### 7.1 核查方法（可复现）

把后端所有 `**/controller/**/*.java` 的类级 `@RequestMapping` 与方法级 `@*Mapping` 拼成完整路径，与前端 `api/index.js` 的 `request.<verb>('路径')` 做双向比对。

**三个必须注意的坑**（踩过，都会产生成片假阳性）：

1. **模板变量要展开成具体值**，不能压成通配。`${mediaType}` 必须展开成 `image` / `audio` 两个具体路径，否则与后端的 `/api/image/...` 对不上；`${action}` 展开成 `view` / `download` / `play`。
2. **`/api` 前缀两边都要归一化**：knowledge 模块的 Controller 类级带 `/api`（`/api/knowledge-graph`），而 base-service / workorder / ops 不带（`/workorder`）。
3. **别漏原生 `fetch`**：`ChatPage` 的流式对话走 `fetch('/api/ai/chat/stream')` 而非 axios 实例，只扫 `api/index.js` 会看不见它。

### 7.2 「后端有、前端未接入」的 4 条

| 接口 | 判定 |
|------|------|
| `POST /ai/chat/stream` | **已接入**。`ChatPage.vue` 用原生 `fetch` 调用（SSE 需要），审计脚本的盲区 |
| `GET /system/intent/list` | **后端冗余**。前端用的是 `/system/intent/listAll`，`/list` 无调用方 |
| `GET /system/slot/list` | **后端冗余**。同上，前端用 `/system/slot/listAll` |
| `POST /open/webhook/inbound/receive/**` | **设计如此**。入站回调由外部业务系统调用，前端不应调用 |

> 前两条的 `/list` 接口是后端遗留的无调用方接口，**可清理也可保留**，不影响功能。

### 7.3 一条曾误判为「契约不一致」的项

`recordMediaAction(mediaType, fileId, action)` → `POST /api/{image|audio}/enhance/stats/{fileId}/{action}` 曾被认为与后端不匹配。**实际不是**：当 `action` 取 `view` / `download` / `play` 时，它生成的 URL 与后端的具名映射 `/stats/{fileId}/view`、`/download`、`/play` **完全一致**。

唯一的实际状况是：**该函数目前没有任何页面调用**，所以后端那 4 个统计上报接口处于「已实现、前端未接」状态。等有页面需要上报浏览/播放/下载时，直接调它即可，**前后端都不需要改**。

## 8. 岗位角色的 RBAC 种子数据未落地

前端已实现**五个岗位角色**（`AGENT` / `SUPERVISOR` / `KNOWLEDGE_OPS` / `ADMIN` / `SUPER_ADMIN`）与按角色的菜单矩阵
（见 [前端信息架构 §3.9](前端信息架构.md)）。**演示模式已可用**（mock 里有对应演示账号）。

但真实后端还需要补三样，否则用真后端登录时岗位角色不生效：

| 待补 | 内容 |
|------|------|
| `cs_role` 种子行 | 目前只有 `SUPER_ADMIN` / `AGENT` / `ADMIN` 三行，缺 `SUPERVISOR`、`KNOWLEDGE_OPS` |
| `cs_user_role` 关联 | 新岗位的演示账号与角色的绑定关系 |
| `cs_role_menu` 授权 | 角色 → 菜单/权限的授权数据，否则后端下发的 `permissions` 与前端菜单对不上 |

> 前端菜单目前**只读登录返回的 `roles` 数组**，不依赖 `permissions`；但后端做接口级鉴权时仍需 `cs_role_menu`。
> **安全提醒**：前端菜单过滤**不是安全边界**。真正挡住越权要靠后端接口鉴权——前端只是把不该出现的入口藏起来。

## 9. 维护约定

- **实现某个占位方法后**：从本文删掉对应行（含 §2.1），并同步更新 [接口说明](接口说明.md) 里该节的「占位实现」标注
- **新增占位接口**：严格按 §1 的三种风格写，**不要假装成功**；查询类必须返回 `implemented=false`；鉴权类占位**必须失败关闭**（返回 `false`），不得默认放行
- **登记占位**：内部方法桩必须在 §2.1 登记「按设计应实现 / 当前行为 / 失败特征」三项——前端读不到 `implemented` 标记，只能靠本文提示
- **前端**：读到 `implemented=false` 或进入内存桩页时显示「**后端未完成**」横幅，**不要在界面上暴露接口路径与前后端分工**
- 本文只记「后端未完成」，接口字段与示例见 [接口说明](接口说明.md)
