## 1. 目标与范围

**AI 可以"提议"高危操作，但永不自行执行。** 执行必须由具备权限的人在坐席台显式确认，且全程幂等、可审计、可追溯"谁在何时同意了什么参数"。

典型场景：发放优惠券、同意客户退货/退款、修改订单、冻结账户——这些操作的共同点是**对方系统状态会被真实改变且难以撤销**。

**不在本设计范围内**：客户本人确认（如需，应另做带短信验证的独立流程）、审批流引擎（Flowable 默认关闭，不引入）、`read` 级工具的限制（查物流等只读操作允许 AI 直接执行）。

## 2. 现状盘点

### 2.1 已落地（不要重复造）

| 能力 | 位置 |
|---|---|

## 3. 总体流程

```
用户 ──▶ agent：意图识别命中高危意图（退款/发券）
          │  抽取参数（entityId、金额…）→ 计算幂等键
          ▼
open：五道关卡 ──第 4 关命中──▶ 落待确认记录(status=CONFIRMING，**不占幂等键**)
          │                       返回 confirm-required + confirmId + expireAt
          ▼
会话：渲染「待确认卡片」（工具名 + 参数摘要 + 剩余有效时间）
          ▼
坐席台：待确认列表 ──点击「同意」──▶ POST /open/tool/confirm（JWT 用户 + 租户校验）
          ▼
open：校验状态 ──此刻才写入幂等键并抢占执行权──▶ 连接器出站 ──▶ 回写 SUCCEEDED/FAILED
          ▼
会话：向用户推送执行结果（成功/失败/拒绝/过期）
```

> 当前实现范围：**「挂起 → 通知 → 确认 → 执行 → 回写 → 推送」已闭环**：open 侧状态机与执行、
> 坐席台页面与会话卡片、WS 状态推送、超时 job 均已落地；AI 侧由 `FunctionCallService.autoSelectAndExecute` 选工具。
> `critical` 双人复核仍为预留。
> 同一「租户 + 会话 + 工具 + 参数快照」反复 invoke 会复用未过期的待确认记录，不会堆重复待办。

## 4. 状态机

```
(发起) ─▶ CONFIRMING ──同意──▶ CONFIRMED ──▶ SUCCEEDED / FAILED
            │  │                 ↑ 幂等键在此刻写入
            │  └──坐席拒绝──▶ REJECTED（通知用户，可重新发起）
            ├──超时(expire_at)──▶ EXPIRED（通知用户；再执行须重新发起）
            └──取消(发起方改口/会话结束)──▶ CANCELLED
```

- 终态（SUCCEEDED/FAILED/REJECTED/EXPIRED/CANCELLED）不可再流转；
- 过期用**惰性判断**（读列表/确认时判）+ `ToolConfirmExpireTask` **每分钟兜底扫描**（Redis 锁、单批 200、条件更新不覆盖已确认单），长时间无人访问的过期行也会被落库为 `EXPIRED` 并推送 `tool-confirm-expired`；
- `read` 级工具无需确认，记录创建即为 `CONFIRMED`；
- `CONFIRMED` 是"已抢占执行权、结果尚未回写"的中间态：再次确认会先按幂等键重放/返回「正在执行中」，**绝不二次出站**。

## 5. 数据模型

**推荐复用 `cs_open_tool_invoke` 加字段**（而不是新表）：审计连续（一条记录从待确认走到执行结果）、幂等唯一索引本就在这张表、避免两表关联。

```sql
ALTER TABLE `cs_open_tool_invoke`
  ADD COLUMN `tenant_code`     VARCHAR(64) NOT NULL DEFAULT 'default' AFTER `session_id`,
  ADD COLUMN `status`          VARCHAR(16) NOT NULL DEFAULT 'CONFIRMING'
        COMMENT 'CONFIRMING/CONFIRMED/SUCCEEDED/FAILED/REJECTED/EXPIRED/CANCELLED',
  ADD COLUMN `risk`            VARCHAR(16) DEFAULT NULL COMMENT '发起时风险等级快照',
  ADD COLUMN `requested_by`    VARCHAR(64) DEFAULT NULL COMMENT '发起方标识(坐席/访客ref/AI)',
  ADD COLUMN `confirmed_by`    VARCHAR(64) DEFAULT NULL COMMENT '确认人(JWT用户名，服务端取)',
  ADD COLUMN `confirmed_at`    DATETIME DEFAULT NULL,
  ADD COLUMN `rejected_reason` VARCHAR(255) DEFAULT NULL,
  ADD COLUMN `expire_at`       DATETIME DEFAULT NULL COMMENT '空=不过期',
  ADD COLUMN `update_time`     DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  ADD KEY `idx_open_invoke_status` (`status`, `tenant_code`);
```

三个关键点：

1. **`CONFIRMING` 行的 `idempotency_key` 必须为 NULL**：未确认不占键（MySQL 允许多个 NULL 并存，正好承载该语义），确认那一刻才写入；
2. **`tenant_code` 进表后，所有查询必须带租户口径**（`JwtContext.resolveTenantCode`），与 `FaqController` 一致；
3. `request_json` 已是发起时的参数快照，确认页直接展示；**前端只展示白名单字段**（金额/券号/订单号），不要把整个 payload 丢给确认者。

> 配置项：`open.tool.confirm-expire-minutes`（默认 30，0 或负数表示不过期），已由 `OpenToolProperties` 消费并写入 `expire_at`；登记见 [配置说明](配置说明.md)。
>
> **存量库迁移（务必按顺序）**：`status` 列带默认值 `CONFIRMING`，直接 ALTER 会把历史调用记录全部变成"待确认"。
> 迁移脚本必须在 `ALTER` 后**立即**回填历史行，再发布新代码：
>
> ```sql
> ALTER TABLE `cs_open_tool_invoke`
>   ADD COLUMN `tenant_code`     VARCHAR(64) NOT NULL DEFAULT 'default' AFTER `session_id`,
>   ADD COLUMN `status`          VARCHAR(16) NOT NULL DEFAULT 'CONFIRMING' COMMENT '...',
>   ADD COLUMN `risk`            VARCHAR(16) DEFAULT NULL,
>   ADD COLUMN `requested_by`    VARCHAR(64) DEFAULT NULL,
>   ADD COLUMN `confirmed_by`    VARCHAR(64) DEFAULT NULL,
>   ADD COLUMN `confirmed_at`    DATETIME DEFAULT NULL,
>   ADD COLUMN `rejected_reason` VARCHAR(255) DEFAULT NULL,
>   ADD COLUMN `expire_at`       DATETIME DEFAULT NULL,
>   ADD COLUMN `update_time`     DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
>   ADD KEY `idx_open_invoke_status` (`status`, `tenant_code`);
>
> -- 历史行都是已执行/已失败的调用，不是待确认
> UPDATE `cs_open_tool_invoke`
>    SET `status` = CASE WHEN `success` = 1 THEN 'SUCCEEDED' ELSE 'FAILED' END
>  WHERE `idempotency_key` IS NOT NULL OR `success` IS NOT NULL;
> ```

## 6. 接口设计

均在 `ai-cs-open`（网关 `/open/**`，需登录）。**注意 `ai-cs-open` 未引入 Swagger 依赖，不要写 `@Operation`，接口说明沿用 Javadoc。**

| 接口 | 方法 | 权限 | 实现状态与口径 |
|---|---|---|---|
| `/open/tool/invoke`（已存在） | POST | 登录用户 | ✅ 命中 `confirm-required` 时落/复用 `CONFIRMING` 记录，`ToolInvokeResultDTO` 增补 `confirmId` / `status` / `expireAt` |
| `/open/tool/pending` | GET | `tool:confirm` + 租户校验 | ✅ 参数 `pageNum`(默认 1) / `pageSize`(默认 10，上限 100) / `tenantCode` / `sessionId` / `status`；按 `expire_at` 升序（快超时的在前） |
| `/open/tool/pending/{id}` | GET | 同上 + 归属校验 | ✅ 详情：`requestJson` 参数快照、发起人、`sessionId`、风险等级、确认人与时间 |
| `/open/tool/confirm` | POST | 同上 + **必须 JWT 用户（禁访客）** | ✅ 入参 `confirmId` + 可选 `idempotencyKey`；确认时**重跑关卡 1~3**（工具/行业包/连接器可能已变化），第 4 关不再拦 |
| `/open/tool/reject` | POST | 同上 | ✅ 拒绝 + 理由（超 255 字截断） |
| `/open/tool/cancel` | POST | 发起方本人或坐席 | ✅ 用户改口 |

- `confirmed_by` **只从 `JwtContext.getCurrentUsername()` 取，禁止请求体传入**；
- 归属校验：令牌租户非空时必须匹配记录租户；**平台级账号（令牌未绑定租户）可跨租户运营**，仅当其显式传了 `tenantCode` 时才校验；
- `read` 级工具的调用不需要确认接口参与；
- `status` 过滤值只接受状态机枚举，非法值直接报错（避免"查不到就以为没有待办"）；
- 确认接口一律**先条件更新抢占**（`WHERE status='CONFIRMING'`）再出站，两人同时点只有一个真正执行。

> 注意：`ai-cs-open` 未引入 Swagger，接口文档以上表 + Controller Javadoc 为准，详见 [接口说明](接口说明.md)。

## 7. 幂等与一致性

| 场景 | 规则 |
|---|---|
| 键生成 | `{tenant}:{sessionId}:{toolName}:{sha1(参数快照)}`，实现见 `ToolInvokeSnapshot.idempotencyKey()`；超 128 字符时退化为 `{tenant}:{sha1(整键)}`，与列宽对齐 |
| 写入时机 | **确认那一刻**才写键并抢占执行权；`ConnectorInvokeRecorder` 已用 `REQUIRES_NEW` 独立事务避免污染主链路 |
| 重放 | 该键已 `SUCCEEDED` → 直接重放首次结果，`source=idempotent`；待确认行再次确认也走这条 |
| 并发双人同时确认 | 带条件的 `UPDATE ... WHERE status='CONFIRMING'`（乐观锁），影响行数 0 → 后者先查键：已成功则重放，否则提示「正在执行中/已处理」 |
| 已确认未回写（进程中断） | 行停在 `CONFIRMED`：再次确认只按幂等键重放，查不到结果则明确提示「正在执行中」，**不会二次出站** |
| 与外部系统 | 先落库后出站；失败只改状态，不删记录 |

## 8. 通知与前端

**已落地（2026-11-25）**：

- **坐席台「待确认」页**：路由 `/workspace/pending`，菜单「待确认」+ 红点 badge；每 **5 秒**轮询
  `GET /open/tool/pending?status=CONFIRMING`，支持详情核对、同意、拒绝、取消；
- **会话确认卡片**：`ToolConfirmCard.vue`，在 `ChatPage` / `WorkspacePage` 按 `confirmId` 渲染，
  展示工具名、参数摘要（仅白名单字段：单号/金额/券号/原因）、剩余有效期；
- **WS 状态推送**：确认/拒绝/执行结果推 `tool-confirm-result`，超时推 `tool-confirm-expired`，
  卡片与列表按 `confirmId` 原地收敛；推送经 Redis 频道 `ws:push`，多副本可达；
- **超时兜底**：`ToolConfirmExpireTask` 每分钟扫描过期 `CONFIRMING`，落库 `EXPIRED` 并推送；
- **降级**：`open.tool.confirm-push-enabled=false` 或 Redis 不可用时只落库，前端靠轮询刷新。

**仍待做**：`cs_card_template` 进气泡（目前确认卡为前端内置组件，不是模板化卡片）、`critical` 双人复核。

## 9. 安全边界

1. **AI 无执行权**：`needConfirm` 是服务端配置，`FunctionCallService`（CONSULT/default 分支）恒传 `confirmed=false`，模型输出该字段一律忽略；
   ⚠️ **已知风险一**：`OpenPlatformService.invoke` 第 4 关仍是 `needConfirm(tool) && !Boolean.TRUE.equals(dto.getConfirmed())`，
   **受信的直接调用方**（内部脚本、已登录员工直接 POST `/open/tool/invoke`）传 `confirmed=true` 仍可跳过人工确认；
   ⚠️ **已知风险二**：`AiAgentService.routeToTool`（REFUND/QUERY_LOGISTICS 意图）仍按「用户消息含『确认』」置 `confirmed=true`，
   即 AI 侧存在一条可跳过人工确认的历史路径。建议两处统一收敛：服务端忽略 `invoke` 的 `confirmed` 字段，
   仅 `ToolConfirmService.confirm()` 链路可置真；`routeToTool` 改为恒 `false`（届时本文 §11 第 1 条才真正成立）；
2. **确认人必须是人**：访客令牌在网关就被限制在聊天路径（`VISITOR_ALLOWED`），确认接口再加权限点双保险；
3. **参数必须给人看**：防 AI 抽错金额/券号；
4. **不能迟到执行**：`expire_at` 过期即拒；会话结束的待确认也应失效；
5. **全程留痕**：request/response + 发起人 + 确认人 + 时间 + 拒绝理由；
6. `critical` 双人复核：字段预留（`confirmed_by` 可扩展），先单人。

## 11. 验收标准

1. AI 侧调用 `apply_refund` → 因 `confirmed=false` 命中第 4 关，落 `CONFIRMING` 记录并返回 `confirmId`（**已可验**）；
   ⚠️ 直接 POST `/open/tool/invoke` 传 `confirmed=true` 目前**仍会被执行**（旁路未收敛），见 §9 第 1 条；
2. 未经确认的调用不产生幂等占位行，但会生成一条 `CONFIRMING` 待确认记录并可被复用（**已可验**）；
3. 坐席确认后执行成功；同一幂等键二次确认 → 重放首次结果，不二次退款（**已可验**）；
4. 两个坐席同时确认同一 `confirmId` → 只有一个成功（**已可验**）；
5. 过期后确认 → 拒绝并提示重新发起（**已可验**，需把 `confirm-expire-minutes` 调小或改库时间）；
6. 待确认列表按租户隔离：A 租户坐席看不到 B 租户的（**已可验**）；
7. 审计记录含 `confirmed_by` / `confirmed_at` / `request_json`（**已可验**）。

## 12. 推荐默认值

- 确认人：**坐席或租户管理员（单人）**；`critical` 预留双人；
- **客户本人不可确认**（否则等于 AI 代执行）；确有需要就另做带短信验证的独立流程；
- 超时 **30 分钟**，超时后转人工话术；
- `read` 级（查物流）**允许 AI 直接执行**；
- 存储：**复用 `cs_open_tool_invoke` 加字段**。

## 13. 实现与健壮性检测

### 13.2 本轮健壮性检测发现并修复的问题

| # | 问题 | 影响 | 修复 |
|---|---|---|---|
| 1 | `ToolConfirmService` 调用了不存在的 `executeAfterConfirm(dto, tenantCode)` | **编译失败**，整个模块不可发布 | 补齐 `OpenPlatformService.executeAfterConfirm(dto)` |
| 2 | `invoke` 第 4 关只返回 `confirm-required`，从不落待确认记录 | 确认接口拿不到 `confirmId`，功能不可用 | 新增 `findOrCreatePending()` 并在第 4 关调用 |
| 3 | `open.tool.confirm-expire-minutes` 有配置无消费方 | 待确认永不过期 | 挂起时写入 `expire_at` |
| 4 | 平台级账号（令牌无租户）被 `assertTenant` 默认成 `default` | 平台运营无法处理其他租户待办，与设计不符 | 令牌无租户时允许跨租户，显式传 `tenantCode` 时才校验 |
| 5 | 分页参数未兜底 | 负数/超大 `pageSize` 触发 SQL 异常或慢查询 | `pageNum≥1`、`pageSize∈[1,100]` |
| 6 | `status` 过滤值透传任意字符串 | 拼错状态返回空列表，被误判为"没有待办" | 只接受枚举名，非法值明确报错 |
| 7 | 请求体 `idempotencyKey` / `reason` 超列宽 | 数据库报错导致整笔确认失败/回滚 | 键超 128 直接拒绝，理由超 255 截断 |
| 8 | 行停在 `CONFIRMED`（执行中/进程中断）只能看到「已处理」 | 无法判断是否成功，也无法恢复 | 单独分支：按键重放，查不到则提示「正在执行中」 |
| 9 | 确认后执行使用的幂等键与落库键可能不一致 | 重放定位错误 | 执行前 `dto.setIdempotencyKey()` 对齐 |
| 10 | 存量库 ALTER 后历史记录默认 `CONFIRMING` | 历史调用全部出现在待确认列表 | 文档补充迁移回填 SQL（见 §5） |

### 13.3 已知限制（后续批次处理）

- **`confirmed=true` 旁路**：直接调用 `/open/tool/invoke` 的受信方可跳过人工确认；`AiAgentService.routeToTool` 也仍按「消息含确认」置真。两处都需收敛，统一改为服务端忽略该字段；
- **无唯一索引去重**：同参数并发首次 invoke 仍可能产生两条待确认记录（确认侧条件更新保证不会重复执行）；
- **`critical` 双人复核未做**：字段已预留，当前仍单人确认；
- **模板化卡片未接**：确认卡为前端内置组件，尚未走 `cs_card_template` 进气泡；
- **`tool:confirm` 未进 RBAC 种子**：`SUPER_ADMIN` 正常，其他角色需在角色管理里授权（见 [后端未完成清单 §8](后端未完成清单.md)）；
- **执行与回写非原子**：连接器已出站但进程中断时，记录停在 `CONFIRMED`，需按幂等键人工核对对方系统结果；
- **推送依赖 Redis**：Redis 不可用时只落库不推送，前端退回 5 秒轮询（不影响状态正确性）。

### 13.4 自验方式

```bash
# 1) 未确认调用：应返回 source=confirm-required，且带 confirmId/status/expireAt
POST /open/tool/invoke  {"toolName":"apply_refund","entityId":"ORD001","sessionId":"s1"}

# 2) 待确认列表（需 tool:confirm）
GET /open/tool/pending?pageNum=1&pageSize=10&status=CONFIRMING

# 3) 确认：成功后返回 source=real/mock，状态 SUCCEEDED；重复确认走重放
POST /open/tool/confirm {"confirmId":1}

# 4) 拒绝 / 取消
POST /open/tool/reject {"confirmId":2,"reason":"金额不符"}
POST /open/tool/cancel {"confirmId":3,"reason":"用户改口"}
```
